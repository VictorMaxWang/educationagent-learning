# B站搜索恢复与整视频时长范围

## 诊断依据

2026-10-16，同一公开BV在本机CPython和JDK默认DIRECT链路均得到详情HTTP200/code0；服务器首页和综合搜索200，但详情412。生产采用的 `/x/web-interface/view` 仍与当前bilibili-cli所调用的SDK详情入口、OpenCLI视频适配一致，不能通过更换同一接口的包装工具保证恢复。没有更改代理、账号、IP或挑战处理。

最小多分P实测：`BV1Fb7h6iEeD` 的当前搜索时长为 `2:46`（166秒），详情总时长166秒，两个分P分别116和50秒。搜索没有pages/videos字段，is_union_video=0也不能说明单P。该证据支持以搜索所报总时长处理整条视频，不能把166秒标成P1时长。原始结果在本地 `target/qq-bili-repair-20261016/search-duration-probe.json`。

## 实现行为

1. 继续优先原有搜索与详情路径；详情正常成功时仍使用真实分P及其时长。
2. 第一次详情HTTP/API 412后，该任务不继续请求被限详情端点；优先采用本次成功搜索的整视频元数据。
3. 搜索必须HTTP200/code0，条目为video、有合法BV、非空标题和作者、明确非付费标记以及严格可解析的正时长。广告、付费或格式不明访问标记、冲突的重复BV、原生视频删除响应均排除。
4. 时长仅按明确 `M:SS` / `H:MM:SS` 解析，整条总时长加入原组合预算。已知超预算不能借某个未经核验的短分P进入推荐。未知时长仅能退到已有、同BV及标题作者严格匹配且24小时内的真实详情缓存；无可靠来源则隐藏。
5. 整视频使用 `id=BV…:whole`、`part=0`、`durationScope=whole-video`、`verificationScope=search-metadata`、`sourceKind=bilibili-search-metadata`，外链不带p参数。它不会写入详情核验缓存，也没有伪造pages/state或详情成功状态。
6. 卡片显示“B站搜索资料”“整条视频 2:46”和实际查询时间。现有分类、适龄与教学目标匹配、元数据引用、向量及组合优化继续生效；同BV的整视频与分P互斥。
7. JSON/ZIP/HTML/讲稿/PPTX链路采用明确范围字段；无p参数不能默认补成p=1，整条时长与分P地址矛盾时拒绝。导入一律是历史入口，不继承线上ready或核验状态。

核心代码：`BilibiliVideoCatalog`、`ClassroomRecommendationService`、`ClassroomSupplementaryResources`、前端`SupplementaryVideos`与`export/supplementary.ts`。检索版本随实现升级，使旧失败缓存不会掩盖恢复后的结果。

## 验证状态

新增测试先于实现，覆盖166秒整条语义、412只请求一次、失败搜索/未知时长/付费/广告/冲突条目排除、原生删除不转搜索兜底、整视频公开字段及不补p的课包往返。统一构建及正式站验收由根任务执行后追加；此文不将源码完成写成上线成功。
